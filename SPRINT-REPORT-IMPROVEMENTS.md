# Sprint Reporting — Improvements & New Weekly Scorecard (Handoff Spec)

> **Purpose of this doc.** Hand this to a fresh Claude Code session opened **in this
> project** (`product-development-performance-dashboard`). It specifies (1) a shared
> template for our two sprint reports, (2) concrete improvements to the existing
> **per-sprint Sprint Summary** generator, and (3) how to add a **new Weekly Scorecard**
> generator that mirrors the Sprint Summary feature. Everything references real files,
> functions, and types already in this repo.

---

## 0. Orientation (read first)

**What this app is:** a Next.js/TypeScript dashboard that reads the team's Asana export
from a Google Sheet and computes sprint metrics. Data flow:

```
Google Sheet (Asana export)
  → fetchSheetRows()            src/lib/sheets.ts          (raw string[][], 60s cache)
  → mapRowsToSprintRows()       src/lib/row-mapper.ts      → SprintRow[]  (src/types/sprint.ts)
  → engines (src/lib/*-engine)  compute metrics
  → API routes (src/app/api/*)  serve JSON / post to Asana
  → pages + components          render / operator "Send to Asana"
```

**The two reports we produce:**

| Report | Cadence | Generated by | Posted to Asana as |
|---|---|---|---|
| **Sprint Summary** (per-sprint) | End of each sprint | `sprint-summary-engine.ts` + `sprint-summary-asana.ts` (EXISTS — **change destination to a subtask, Section 2.5**) | `Sprint Summary: <sprint>` **subtask** under parent task `1216367392606773` ("DEV - End of Sprint Summary"), assigned to Shann |
| **Weekly Scorecard** (weekly) | Weekly | **does not exist yet — build it (Section 3)** | `(ST) 🗒️ Product Development Sprint Scorecard Report (MM/DD/YYYY)` **subtask** under parent task `1207376779108203` ("Dev - Weekly Scorecard Report") |

> **Both reports are now subtasks under standing parent tasks** (not standalone tasks in the
> project). This is the one shared prerequisite: a `createAsanaSubtask()` helper in
> `asana.ts` (Section 2.5) that both `scorecard-asana.ts` and `sprint-summary-asana.ts` use.

**Key building blocks already in the repo (reuse these — do not re-implement):**

- `computeSprintSummary(rows, sprintId)` — `src/lib/sprint-summary-engine.ts`
- `computeBurndown(rows, allottedPoints)` → `{ totalConsumedPoints, burndownRate, days[], qaFlags[] }` — `src/lib/burndown-engine.ts`
- `getUniqueSprints(rows)`, `resolveNextSprintName(rows, sprintId)` — `src/lib/burndown-engine.ts`
- `computeSummary(rows)` → `{ totalTasks, totalCompleted, completionRate }` — `src/lib/completion-rate-engine.ts`
- `computeSprintStats(rows)` → per-sprint `{ sprintId, completionRate, total, completed, ... }[]` (chronological) — `src/lib/completion-rate-engine.ts`
- `filterBySprints`, `filterByRoles`, `filterByYears` — `src/lib/completion-rate-engine.ts`
- `DEV_MEMBERS`, `isDevMember(name)` — `src/lib/dev-members.ts`
- `generateFocusSummary(sprintName, titles)` (Gemini, never throws) — `src/lib/sprint-focus-summary.ts`
- Asana writes: `createAsanaTask()`, `postCommentToTask(gid, text, {asHtml, pinned})`, `postGroupedTaskListInChunks()`, `buildGroupedListHtmlChunks()` — `src/lib/asana.ts`
- `formatHours(n)` — `src/lib/format.ts`
- `SprintRow` fields available: `storyPoints`, `hoursEstimate`, `hoursActual`, `status` (`"Complete"`), `role` (`"Developer"`, `"QA Tester"`, `"Product Specialist"`…), `assigneeName`, `linkToTask`, `tasksTitle`, `recurringTask` (`(DT)/(WT)/(ST)`), `week`, `month`, `year`, `sprint`, `sprintDateStart/End`.

**Asana comment HTML gotcha (already handled by `asana.ts`, keep it that way):** comment
bodies are single-line compact `<body><strong>…</strong><ol><li>…</li></ol></body>`. Do
**not** introduce indentation/newlines between `<li>` tags — Asana renders those as blank
bullets.

## 1. Consolidated Template Proposal

Two reports, two audiences. Keep them separate but make each complete for its reader.

### 1A. Weekly Scorecard (leadership health dashboard)

| # | Field | Source |
|---|---|---|
| 1 | Sprint/period + date range | sprint id + dates |
| 2 | **Completion Rate — this sprint** + **goal/target** (e.g. ≥95%) | `computeSummary` |
| 3 | **Completion Rate — QTD** (quarter-to-date trend) — *replaces YTD* | `computeSprintStats` filtered to quarter |
| 4 | Individual Completion Rate — **Devs %** and **Product Development Team %** | `computeSummary` + role/dev filter |
| 5 | **Burndown** — allotted / consumed story points + burndown rate | `computeBurndown` |
| 6 | **Uptime** — % downtime HAS & MyHF | **manual input** (not in sheet) |
| 7 | **Summary narrative** — analytical "why the numbers moved" | Gemini (new analytical prompt) |
| 8 | cc / stakeholders | static config |

### 1B. Per-Sprint Summary (operational sprint ledger)

| # | Field | Status |
|---|---|---|
| 1 | Sprint id | ✅ exists |
| 2 | Focus (what was worked on) | ✅ exists (`focusSummary`) |
| 3 | Completed / Plotted / Carried-Over counts | ✅ exists |
| 4 | Completion Rate % | ✅ exists |
| 5 | Total Estimated vs Actual Hours | ✅ exists |
| 6 | Per-assignee: completed vs plotted % | ✅ exists |
| 7 | Per-assignee: actual vs estimate hours | ✅ exists |
| 8 | Task-link lists (Completed / Carried-Over / Incomplete / Next Sprint) | ✅ exists |
| 9 | **Story points: plotted vs consumed + burndown rate** | ➕ ADD (Section 2.1) |
| 10 | **Trend line: this-sprint vs QTD (or rolling-3-sprint)** | ➕ ADD (Section 2.2) |
| 11 | **Uptime passthrough** (optional) | ➕ ADD (Section 2.4) |

### Shared vs unique

- **Overlap (already or soon in both):** completion rate %, task counts, per-group/per-person breakdown, effort. These are fine to duplicate — different granularity for different readers.
- **Unique to Scorecard:** burndown/story-points, uptime, QTD trend, goal, analytical narrative, cc. (Story-points + trend get added to the Summary too, per #9–10.)
- **Unique to Summary:** full task-link inventory, per-named-assignee hours, next-sprint plan.

### Decisions already agreed (apply these)

1. **Drop YTD from the Scorecard.** A cumulative year-to-date rate goes flat as the
   denominator grows and the metric already sits at ~97–98%, so it carries no signal and
   drives no action.
2. **Use QTD (quarter-to-date) as the trend instead** — it aligns with the team's Traction/EOS
   quarterly cadence (`Sprint #2026.Q2.S7`). Rolling-3-sprint average is an acceptable
   alternative; if unsure, implement QTD and leave a `// TODO rolling` note.
3. **Show a goal/target next to the completion rate** (config constant, default 95%).

## 2. Improve the existing Per-Sprint Summary generator

**Files:** `src/types/sprint-summary.ts`, `src/lib/sprint-summary-engine.ts`,
`src/lib/sprint-summary-asana.ts`. (No route changes needed — routes already recompute
server-side.)

### 2.1 — Add story points + burndown rate

**Why:** the Summary reports hours but not story points; the Scorecard leans on story-point
burndown. Add it so the Summary is self-sufficient.

1. In `SprintSummaryResponse` (`src/types/sprint-summary.ts`) add:
   ```ts
   totalStoryPointsPlotted: number;   // sum of storyPoints across all sprint tasks
   totalStoryPointsCompleted: number; // sum of storyPoints where status === "Complete" && !carriedOver
   storyPointBurndownRate: number;    // completed / plotted * 100 (0 when plotted === 0)
   ```
2. In `computeSprintSummary()` (`src/lib/sprint-summary-engine.ts`): while iterating
   `sprintTasks`, accumulate `parseFloat(row.storyPoints) || 0` into plotted, and into
   completed when `completed` is true. Return the three new fields.
3. In `buildSummaryCommentText()` (`src/lib/sprint-summary-asana.ts`) add lines after the
   hours line:
   ```
   Story Points (Completed / Plotted): 128 / 152
   Story Point Burndown Rate: 84.21%
   ```

### 2.2 — Add a trend line (this-sprint vs QTD)

1. Add to `SprintSummaryResponse`:
   ```ts
   qtdCompletionRate: number | null; // quarter-to-date, null if quarter can't be parsed
   ```
2. Add a helper (engine): parse the quarter from the sprint id and aggregate all rows in the
   same year+quarter **up to and including** the selected sprint, then reuse `computeSummary`:
   ```ts
   // "Sprint #2026.Q2.S7 (0618-0701)" → { year: "2026", quarter: 2 }
   function parseSprintQuarter(id: string) {
     const m = id.match(/#(\d{4})\.Q(\d)/);
     return m ? { year: m[1], quarter: Number(m[2]) } : null;
   }
   ```
   Aggregate by counts (not by averaging rates): `qtd = completedTasks / plottedTasks * 100`.
   Note `computeSummary`/`computeSprintStats` already exist in `completion-rate-engine.ts` —
   import and reuse rather than re-summing.
3. In `buildSummaryCommentText()` add:
   ```
   Completion Rate (This Sprint / QTD): 98.18% / 97.6%
   ```
   (Fall back to just this-sprint when `qtdCompletionRate` is null.)

### 2.3 — (Optional) analytical enrichment of Focus

Leave `generateFocusSummary` as-is for the Summary (it answers "what"). The analytical
"why" belongs on the Scorecard (Section 3.3). Skip unless the operator asks.

### 2.4 — (Optional) Uptime passthrough

If you want uptime on the Summary too: add optional `uptimeNote?: string` to the
send-to-asana request body, thread it into `buildSummaryCommentText()` as a trailing
`Uptime: <note>` line. It's operator-typed (not in the sheet).

### 2.5 — Change the Asana destination to a subtask under a standing parent

**Why:** the Sprint Summary currently creates a **standalone** `Sprint Summary: <sprint>`
task in project `514125768649585`. It should instead be created as a **subtask** under the
standing parent task **`1216367392606773` ("DEV - End of Sprint Summary")** so all sprint
summaries collect under one parent.

1. **Add the shared subtask helper** to `src/lib/asana.ts` (both reports use it — this is the
   `createAsanaSubtask` referenced in Section 3.5):
   ```ts
   export async function createAsanaSubtask(
     parentGid: string, name: string,
     opts: { assignee?: string; dueOn?: string } = {},
   ): Promise<{ gid: string; permalinkUrl: string }> {
     // Same request/parse shape as createAsanaTask, but POST /tasks with
     //   data: { name, parent: parentGid, assignee?, due_on? }   // NO `projects`
     // Return { gid, permalinkUrl } identically.
   }
   ```
2. In `sendSprintSummaryToAsana()` (`src/lib/sprint-summary-asana.ts`):
   - Replace the `DEFAULT_SUMMARY_PROJECT_ID` destination with a parent-task constant:
     ```ts
     const DEFAULT_SUMMARY_PARENT_TASK_ID = '1216367392606773'; // "DEV - End of Sprint Summary"
     ```
   - Swap the create call:
     ```ts
     const parentGid = process.env.ASANA_SUMMARY_PARENT_TASK_ID ?? DEFAULT_SUMMARY_PARENT_TASK_ID;
     const { gid, permalinkUrl } = await createAsanaSubtask(parentGid, taskTitle, {
       assignee, dueOn: todayDateOnly(),
     });
     ```
   - Everything after (the pinned metrics comment + the grouped task-list comments) is unchanged.
   - Keep `DEFAULT_SUMMARY_ASSIGNEE_ID` (Shann) as-is.

### Acceptance criteria (Section 2)

- `npm run build` + `npm run lint` clean.
- Selecting a recent sprint on `/sprint-summary` and posting to Asana produces a comment
  that now includes the **Story Points**, **Story Point Burndown Rate**, and
  **Completion Rate (This Sprint / QTD)** lines, with all existing fields unchanged.
- QTD equals this-sprint rate for the first sprint of a quarter; matches a hand check for a
  mid-quarter sprint.
- The `Sprint Summary: <sprint>` task now appears **as a subtask under "DEV - End of Sprint
  Summary" (`1216367392606773`)**, not as a standalone task in the project, still assigned to Shann.

## 3. New Weekly Scorecard generator

Mirror the Sprint Summary feature end-to-end. Reuse the engines; do **not** re-derive metrics.

### 3.0 — Files to create

```
src/types/scorecard.ts                         # ScorecardResponse + input types
src/lib/scorecard-engine.ts                    # computeScorecard(rows, opts)
src/lib/scorecard-asana.ts                     # buildScorecardCommentText + sendScorecardToAsana
src/app/api/scorecard/route.ts                 # POST → compute + return JSON
src/app/api/scorecard/send-to-asana/route.ts   # POST → recompute + post to Asana
src/app/scorecard/page.tsx                     # operator UI (mirror sprint-summary page)
src/components/scorecard/ScorecardView.tsx     # render (mirror SprintSummaryView)
```
Plus: one nav entry in `src/components/layout/Sidebar.tsx` and (if using the subtask
destination) one small helper in `src/lib/asana.ts` (see 3.5).

### 3.1 — Types (`src/types/scorecard.ts`)

```ts
export interface ScorecardResponse {
  sprintId: string;                 // the sprint the scorecard reports on (default: latest completed)
  dateRange: string;                // "MM/DD/YYYY – MM/DD/YYYY" from sprint dates

  completionRate: number;           // this-sprint, computeSummary
  completionGoal: number;           // target, default 95
  qtdCompletionRate: number | null; // quarter-to-date trend (replaces YTD)
  totalTasks: number;
  totalCompleted: number;

  devsCompletionRate: number;       // role === "Developer" (or isDevMember) subset
  teamCompletionRate: number;       // whole team

  allottedStoryPoints: number;      // operator input
  consumedStoryPoints: number;      // computeBurndown.totalConsumedPoints
  burndownRate: number;             // computeBurndown.burndownRate (number, strip "%")

  uptimeNote: string;               // operator input, e.g. "0% downtime for HAS and MyHF."

  narrative: string | null;         // analytical summary (Gemini); null if unavailable
  narrativeError: string | null;

  computedAt: string;
}

export interface ScorecardInput {
  sprintId?: string;                // default: most recent completed sprint
  allottedStoryPoints: number;
  uptimeNote?: string;
  completionGoal?: number;          // default 95
}
```

### 3.2 — Engine (`src/lib/scorecard-engine.ts`)

`computeScorecard(rows: SprintRow[], input: ScorecardInput): ScorecardResponse`

- Resolve `sprintId` (default = last of `getUniqueSprints(rows)` that is fully in the past).
- `sprintRows = filterBySprints(rows, [sprintId])`.
- `completionRate/totalTasks/totalCompleted` ← `computeSummary(sprintRows)`.
- `teamCompletionRate` ← same as `completionRate` (whole team).
- `devsCompletionRate` ← `computeSummary(filterByRoles(sprintRows, ['Developer']))`
  (fall back to `sprintRows.filter(r => isDevMember(r.assigneeName))` if roles are sparse).
- `qtdCompletionRate` ← reuse the `parseSprintQuarter` + count-aggregation helper from 2.2
  (extract it to a shared spot, e.g. `completion-rate-engine.ts`, and import in both).
- `consumedStoryPoints`/`burndownRate` ← `computeBurndown(sprintRows, input.allottedStoryPoints)`
  (note `burndownRate` there is a string like `"96.00%"` — parse to number).
- `allottedStoryPoints`, `uptimeNote`, `completionGoal` ← passthrough (goal default 95).
- Keep the engine **pure/sync**; the route attaches `narrative` after the async Gemini call
  (same pattern as `sprint-summary` route + `focusSummary`).

### 3.3 — Analytical narrative

Add `generateScorecardNarrative(...)` to `src/lib/sprint-focus-summary.ts` (or a sibling),
reusing the same Gemini plumbing (`resolveModel`, timeout, never-throws contract). Different
system prompt — feed it the computed **numbers** (this-sprint rate, QTD, devs vs team,
burndown, hours if desired) and ask for a 3–5 sentence analytical summary of drivers
(capacity, UTOs, scope shifts), not a task list. Return `{ summary, error }`.

### 3.4 — Compute route (`src/app/api/scorecard/route.ts`)

Mirror `src/app/api/sprint-summary/route.ts`: `runtime='nodejs'`, `maxDuration=60`,
`fetchSheetRows` → `mapRowsToSprintRows` → `computeScorecard` → attach `narrative` via
`generateScorecardNarrative` → return JSON. Validate `allottedStoryPoints` is a positive
number.

### 3.5 — Send-to-Asana (`src/lib/scorecard-asana.ts` + route)

- `buildScorecardCommentText(sc: ScorecardResponse): string` — plain-text body matching the
  current production scorecard shape (headings padded with blank lines exactly like
  `buildSummaryCommentText`):
  ```
  Sprint Scorecard Report - MM/DD/YYYY
  Sprint: <sprintId>
  Date Range: <dateRange>

  Completion Rate:
      This Sprint: 98.18% (Goal: 95%)
      QTD: 97.6%
      Tasks: 548  Completed: 538

  Individual Completion Rate:
      Devs: 37.50%
      Product Development Team: 96.75%

  Burndown:
      Allotted Story Points: 1600
      Consumed Story Points: 1391
      Burndown Rate: 86.94%

  Uptime: <uptimeNote>

  Summary:
      <narrative>
  ```
- `sendScorecardToAsana(sc)` — mirror `sendSprintSummaryToAsana`. **Destination differs**:
  the scorecard is a **subtask** named `(ST) 🗒️ Product Development Sprint Scorecard Report (MM/DD/YYYY)`
  under parent task `1207376779108203` (env `ASANA_SCORECARD_PARENT_TASK_ID`), assigned to
  the scorecard owner (env `ASANA_SCORECARD_ASSIGNEE_ID`), due today. Post the body via
  `postCommentToTask(gid, body, { pinned: true })`.
  - Use the shared `createAsanaSubtask()` helper added in **Section 2.5** (both reports use
    the same helper — don't duplicate it). The scorecard passes `ASANA_SCORECARD_PARENT_TASK_ID`
    (default `1207376779108203`) as the parent.
- Route `src/app/api/scorecard/send-to-asana/route.ts` — mirror the sprint-summary
  send-to-asana route: recompute server-side, use the operator-reviewed `narrative`,
  `uptimeNote`, `allottedStoryPoints`, and `completionGoal` from the request body.

### 3.6 — Page + component

Mirror `src/app/sprint-summary/page.tsx` and `src/components/sprint-summary/SprintSummaryView.tsx`:
sprint selector (default latest completed), an **allotted story points** input (reuse
`AllottedPointsSelect` from `src/components/burndown/`), an **uptime note** text field, a
**goal** field (default 95), a "Generate" action (calls `/api/scorecard`), a preview that
shows all fields + the editable narrative, and a "Send to Asana" button (calls
`/api/scorecard/send-to-asana`).

### 3.7 — Nav

Add to `NAV_ITEMS` in `src/components/layout/Sidebar.tsx`:
```ts
{ label: 'Weekly Scorecard', href: '/scorecard', icon: '🗒️' },
```

### Env vars to document (add to `.env.local` + README)

```
ASANA_SCORECARD_PARENT_TASK_ID=1207376779108203   # "Dev - Weekly Scorecard Report"
ASANA_SCORECARD_ASSIGNEE_ID=<user gid>            # scorecard owner
ASANA_SUMMARY_PARENT_TASK_ID=1216367392606773     # "DEV - End of Sprint Summary" (Section 2.5)
# SCORECARD_COMPLETION_GOAL can stay a code default (95); env optional
```
(Reuses the existing `ASANA_ACCESS_TOKEN`, `GEMINI_API_KEY`, `TIMEZONE`. Note:
`ASANA_SUMMARY_PROJECT_ID` is no longer used for the Sprint Summary once 2.5 lands — it now
posts under the parent task instead of into the project.)

### Acceptance criteria (Section 3)

- `npm run build` + `npm run lint` clean; new `/scorecard` page renders and appears in the sidebar.
- `POST /api/scorecard` with `{ allottedStoryPoints: 1600 }` returns a `ScorecardResponse`
  whose `completionRate`, `devsCompletionRate`, `teamCompletionRate`, `consumedStoryPoints`,
  and `burndownRate` match the `/completion-rate`, `/individual-cr`, and `/burndown` pages for
  the same sprint (cross-check — these must agree since they share the engines).
- `qtdCompletionRate` equals this-sprint rate for the first sprint of a quarter.
- "Send to Asana" creates the `(ST) 🗒️ …` subtask under `1207376779108203` with the pinned
  scorecard comment; **no YTD line**; goal shown beside the rate.
- Uptime + narrative are operator-editable before sending.

## 4. Suggested build order

1. Add the shared `createAsanaSubtask()` helper in `asana.ts` (Section 2.5) — both reports need it.
2. Section 2 (story points + burndown, QTD trend, **subtask-destination switch**). Small, ships
   value immediately, and validates the QTD helper you'll reuse.
3. Extract the QTD helper (`parseSprintQuarter` + count aggregation) into
   `completion-rate-engine.ts` so both the Summary and the Scorecard import one copy.
4. Section 3 engine → types → routes → asana → page → nav.
5. Verify against the existing pages (they share engines, so numbers must match task-for-task),
   and confirm both reports land as subtasks under their respective parents.
